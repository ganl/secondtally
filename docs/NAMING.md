## 一·补、Aegis 仅支持 Android —— 该不该因此保留名字

用户提出(事实正确):**Aegis 只有 Android 版,本项目支持小程序 + Web + 扩展,  
跨平台是真差异,是否可以据此保留名字?**

结论:**事实成立,但这个优势属于「副标题」,不属于「主名」。**  
主名解决的是"用户凭什么找到你",与功能差异不在同一层。

### 三处逻辑断裂(任一处都足以推翻"因此保留名字")

**断裂一:差异化赢不了搜索入口。**

差异化能说服的是**已经看到你的人**。但搜索入口已被占据——  
99 万装机量 + 13.2k stars + PCMag 编辑之选,`Aegis` 这个词的搜索结果  
在可预见时间内不会让位给新项目。**在"搜 Aegis"这个入口上,永远赢不了。**

功能差异决定的是**转化率**(看到对比后选你),品牌决定的是**获取量**  
(有没有人找得到)。混淆这两层,就会得出"我功能更强所以可以沿用强者的名字"  
这种反向结论。

**断裂二:平台差异是版本事实,不是品牌定位。**

"只有 Android"是竞品当前版本的实现选择,不是它的身份认同。  
Beem Development 若明年出iOS 版,这条差异归零,届时你连话术都失去依托。  
**能被别人随时抹平的差异,不适合刻进名字。**

**断裂三(最关键,最初遗漏):在安全专业受众中,"跨平台"是双刃剑。**

Privacy Guides(被广泛引用的 2FA 推荐源)对桌面验证器的态度是明确的劝退:

> "We highly recommend that you use mobile TOTP apps instead of desktop  
> alternatives as **Android and iOS have better security and app isolation  
> than most desktop operating systems**."

技术原因是桌面端把密码与验证码放在同一台机器上,**丢掉了"你有的东西"  
与"你知道的东西"之间的隔离**——中位数木马同时持有浏览器会话、  
密码管理器、邮箱与验证码,一次性全部得手。

同类论述在多份独立评测中重复出现(2fa.bd、geekchamp 等):  
桌面验证器"用便利换取了隔离性",建议仅用于低风险账号的日常场景,  
**高价值账号(主邮箱、密码管理器、银行)应留在独立手机或硬件密钥上**。

**推论:主打"支持所有平台"在最懂安全的受众那里是扣分项,不是加分项。**  
用户的安全直觉是"验证码越分散越好",看到"全平台可用"的第一反应  
可能是"那岂不是更容易泄露"。

### 由此确定真正的定位表述

**不要说**:"支持所有平台"(触发隔离性质疑)  
**要说**:"在小程序里做到桌面级的加密强度,又不触碰桌面隔离缺陷"

具体落到副标题:

> 自造主名 · 小程序 / 网页 / 扩展三端一致的动态口令验证器

这样同时满足:

1. 微信官方"名称须为两个词以上组合"的硬性要求
2. 亮出 Aegis 打不上的那张牌(跨端一致)
3. 主语落在"小程序"上,避开"桌面验证器"的负面联想

**差异化依然完整保留,只是放在它该在的位置。**

## 二、改名的三层结构(不可混为一谈)

用户确认"代码名也可以调整",但代码名与数据契约必须分开处理:

| 层          | 内容                                                                                             | 可否改名               | 理由            |
| ---------- | ---------------------------------------------------------------------------------------------- | ------------------ | ------------- |
| **用户可见层**  | 小程序标题栏、Web `<title>`/H1、扩展商店名、页面 H1、推广文案                                                       | **必须改**            | 唯一影响用户认知与推广效率 |
| **代码标识符层** | 包名 `@twofa/core`、Go module `twofa/server`、二进制名、`window.twofa`、`TWOFA_*` 环境变量                   | **已改**(2026-10-04) | 纯内部命名,机械替换    |
| **数据契约层**  | `twofa.vault.v1`、`twofa.lock.v1`、`twofa.device.id.v1`、`twofa.device.name.v1`、`twofa.session.*` | **已剥离品牌名**(同上)     | 见下            |

### 数据契约层为何不能动(以及"不能动"从哪一刻开始)

> 2026-10-04 补充:本节论述的是**发布后**的约束。产品尚未上线、  
> 无外部用户数据,故前缀已于当日从 `aegis.` 剥离为 `twofa.`,  
> 详见《已执行》一节。**从发布那一刻起,下面的约束才真正生效。**

这些键下存的是用户设备上**唯一的加密保险库**与**唯一的登录凭据**。  
本项目是端到端加密模型:主密码不上传,服务端无明文。**键名一改,旧保险库就读不出来,  
数据永久丢失——没有找回通道,这是 E2E 的必然结果,不是可以"兼容迁移"的问题。**

其中 `twofa.session.*` 存的是同步服务的访问令牌与刷新令牌,  
改名等于让所有已登录设备静默掉线。

### 2.1 关键修正:原稿的键清单不完整,且这个错误已造成安全缺陷

原稿写:

> 存储键仅在 `packages/core/src/vault/service.ts:45-47` 集中定义三处常量,  
> 全部引用走变量,无字面量散落。

**这句话是错的。** 实际清点(2026-10-03,`grep` 全量扫描)结果是**六族键**,  
散落在三个文件里,且原稿漏掉了其中三族:

| 键                                   | 定义位置                                                              | 原稿是否列出        |
| ----------------------------------- | ----------------------------------------------------------------- | ------------- |
| `twofa.vault.v1`                    | `packages/core/src/vault/service.ts:45`                           | ✅             |
| `twofa.lock.v1`                     | `packages/core/src/vault/service.ts:47`                           | ✅             |
| `twofa.device.id.v1`                | `apps/miniprogram/platform.ts:97`                                 | ❌ 漏           |
| `twofa.device.name.v1`              | `apps/miniprogram/platform.ts:98`                                 | ❌ 漏           |
| `twofa.session.<account>`           | `apps/miniprogram/app.ts:85,92,95`(三处字面量拼接)                       | ❌ **漏,且危害最大** |
| `twofa.web.v1.*` / `twofa.ext.v1.*` | `apps/web/src/platform.ts:25`、`apps/extension/src/platform.ts:26` | ❌ 漏           |

**这个漏项不是文档瑕疵,它已经在产品里造成了一个真实缺陷。**

小程序设置页的"清空本机数据"原本硬编码了三个键:

```ts
// apps/miniprogram/pages/settings/index.ts(修复前)
const keys = ['twofa.vault.v1', 'twofa.lock.v1', 'twofa.device.id.v1'];
for (const key of keys) wx.removeStorageSync(key);
```

**漏掉了 `twofa.session.*`。** 后果:用户点了"我确定,清空"、看到"已清空"、  
应用跳回门禁页,但**同步服务的登录态仍然留在 `wx.storage` 里**——  
刷新令牌未失效、访问令牌未清除。在这个项目里这是格外严重的失误,  
因为服务端设计了**刷新令牌重放即吊销全部刷新令牌**的防护,  
而用户已经明确表达了"我要删除全部数据"的意愿,却没有真正做到。

设备名 `twofa.device.name.v1` 同样被漏掉,清空后仍会显示旧设备名。

**已修复**,方式是把键收敛到单一命名空间常量并按前缀全清:

- `apps/miniprogram/platform.ts` 新增 `STORAGE_NAMESPACE = 'twofa.'`、  
  `sessionKey(accountName)`、`wipeAllStorage()`(按前缀全清,不再列举键名)
- `apps/miniprogram/app.ts` 三处会话键拼接改为调用 `sessionKey()`
- `apps/miniprogram/pages/settings/index.ts` 清空逻辑改为调用 `wipeAllStorage()`
- `packages/core/src/vault/service.ts` 删除死代码 `DEVICE_KEY`  
  (它写的是 `twofa.device.v1`,与小程序实际用的 `twofa.device.id.v1` 不一致,  
  且全项目无任何引用——留着只会误导下一个人)

**这次修复带来一个额外收益:今后改名不再需要逐个追键。**  
新增任何以 `twofa.` 开头的键,都会被"清空本机数据"自动覆盖,  
不会再出现"加了个功能,忘了同步维护清空列表"这类漏项。

### 仍然成立的窗口期判断

原稿这一条是对的,且比它自己意识到的更重要:

> 项目仅一个提交、**未真实部署**,故现在改零代价。一旦有用户落盘即永久锁死。

已核实:**两个提交(`f002702` 首版、`014fcec` Go 服务端),无真实部署,  
无外部用户数据。** 这是剥离品牌前缀的唯一安全窗口。

### 已执行:存储键前缀剥离品牌名(2026-10-04)

用户拍板:**A 级可以改,产品还没发布上线。** 窗口期判断成立,  
七族键已从 `aegis.*` 换成 `twofa.*`。

| 旧键                        | 新键                        |
| ------------------------- | ------------------------- |
| `aegis.vault.v1`          | `twofa.vault.v1`          |
| `aegis.lock.v1`           | `twofa.lock.v1`           |
| `aegis.device.id.v1`      | `twofa.device.id.v1`      |
| `aegis.device.name.v1`    | `twofa.device.name.v1`    |
| `aegis.session.<account>` | `twofa.session.<account>` |
| `aegis.web.v1.*`          | `twofa.web.v1.*`          |
| `aegis.ext.v1.*`          | `twofa.ext.v1.*`          |

**为什么是 `twofa.` 而不是干脆去掉前缀(原建议的 `vault.v1`)** ——  
原建议漏了一个约束:**Web 端的 `localStorage` 是按来源(origin)共享的。**  
同一个域名下的任何页面都能读写它。去掉前缀意味着 `vault.v1` 这种  
泛泛的键名可能与其他页面撞车,而且"清空本机数据"按前缀匹配时  
会把别人的键一起删掉。小程序与扩展的存储是隔离的,但 Web 不是,  
所以前缀必须保留,只是换掉其中的品牌部分。

`twofa.` 描述的是应用品类而非品牌,主名将来换成什么都不必再改 ——  
这正是剥离的目的。**发布后此处即永久冻结。**

配套加了一条测试 `packages/core/test/storage-keys.test.mjs`:  
三端各自硬编码一份前缀,没有任何编译器检查,某一端漏改不会报错,  
只在用户换设备同步时表现为"数据读不出来"。测试把 7 处钉死,  
并用变异验证过(故意改坏 Web 端前缀,测试确实失败)。

### 国际竞品:跨端赛道同样已有人占位

查证 2026 年主流 2FA 产品的平台覆盖,确认"跨端"本身**不是空白市场**:

| 产品                       | 平台                                  | 同步方式                           | 关键约束               |
| ------------------------ | ----------------------------------- | ------------------------------ | ------------------ |
| **Aegis**                | 仅 Android                           | **无内置同步**,靠加密导出文件              | 无 iOS、无桌面、无云同步     |
| **Ente Auth**            | Android/iOS/Windows/macOS/Linux/Web | E2E 加密云同步                      | **必须注册 Ente 账号**   |
| **Proton Authenticator** | Android/iOS/Windows/macOS/Linux     | E2E 同步(需 Proton 账号)或 iCloud    | 2025-07-31 才发布,历史短 |
| **2FAS**                 | Android/iOS + 浏览器扩展                 | 走**用户自己的** iCloud/Google Drive | 扩展依赖手机应用,非独立桌面库    |
| **Google Authenticator** | Android/iOS                         | 绑Google 账号同步                   | 闭源,导出控制弱           |
| **Authy**                | 仅移动(桌面端 2024-03已停止)                 | 厂商服务器                          | **无数据导出能力**,厂商锁定   |


**这组数据有两层含义:**

1. **跨端早已是成熟赛道**,不是空白。Ente Auth 是"跨端 + E2E 同步"的  
   直接竞品,且开源、有桌面客户端、有 Web 端——本项目在功能清单上  
   并不天然领先,营销时**不得暗示"只有我们支持跨端"**,会被 Ente 官方数据直接反驳。
2. **本项目真正的可辩护差异点不是跨端,而是三点组合**:
   - **无需注册账号**(对比 Ente/Proton:不需要把 2FA 托付给另一家服务)
   - **自部署同步** + 服务器无明文(可审计,E2E 模型下服务器无解密能力)
   - **小程序形态**——中国用户不装 App 也能用,这是 Ente/Proton 都不覆盖的场景  
     **尤其第一点值得放大**:Privacy Guides 社区明确指出  
     "Creating an account can mean giving another service some of your personal  
     information and becoming dependent on that service for part of your 2FA setup."  
     (创建账号意味着把部分个人信息交给另一家服务,并在 2FA 环节对其产生依赖)  
     —— 2FAS 被推荐的理由之一正是"不要求用户为E2E 云备份另建账号"。  
     **"免账号"是这个赛道公认的优势项,而本项目天然具备。**

## 四、微信官方命名规则(硬约束)

来自微信官方《常见拒绝情形》与《平台运营规范》原文,直接决定候选合法区间:

1. **名称不是单词汇,必须是两个词以上的组合**,当无法判断时审核人员可主观判断。
2. 不能以**广义归纳类**、普遍且不具有识别性的词汇命名。
3. 不能含**与功能无关的搜索热词**或关键词堆砌,不得"与搜索系统进行规则对抗"。
4. 不能与已有小程序/公众号/**热门应用名称**重复或混淆。
5. 名称须与**服务类目相符**,不能过于宽泛或与实际不符。
6. 长度 **4–30 字符**(一个中文字 = 2 字符)。
7. **年度改名仅 2 次**,发布后改名需重新审核 → **选名要一次到位**。

**推论:微信自己要求"品牌 + 品类"两词结构。** 这排除了纯品类名  
(「动态口令」「验证码」一定驳回),也印证了副标题带品类词是正确做法。

### Chrome 扩展商店相关约束

- 不得侵犯他人商标权,"若认为可能侵犯知识产权,产品可见度会受影响"。

### 六·二、"two factor" 能否融入名字?(2026-10-03 补)

用户提问:"two factor 能不能融入到名字里"。查证后结论:**语义必须用,但只能进副标题,不能进主名。**

#### 第一层约束:法律(最硬,此前几轮全部遗漏)

《商标法》**第十一条第一款第(二)项**:

> 仅直接表示商品的质量、主要原料、**功能、用途**、重量、数量及其他特点的标志,不得作为商标注册。

「双因子」「双重认证」「多因子」「2FA」「OTP」「动态口令」「验证器」——**全部是在直接描述本产品的功能与用途**,落入该项。

**这一条的性质与"被占用"完全不同:**

|        | 被占用    | 落入第十一条            |
| ------ | ------ | ----------------- |
| 性质     | 别人先申请了 | **法律不允许任何人独占**    |
| 换词能否绕开 | 能      | 不能,所有同类描述词都落入     |
| 后果     | 换个名字即可 | 主名无法注册 → 无法形成品牌资产 |

另有 **第五十九条**:注册商标中含有直接表示功能、用途等特点的,  
**权利人无权禁止他人正当使用**。即:即便侥幸注册下来,别人用"双因子"三个字  
描述自己的产品也不构成侵权 —— **注册了也等于没注册**。

**推论:主名里带品类词 = 主名不可注册 = 推广到一定规模会被仿冒且无法维权。**  
这是比"看不懂""撞车"更硬的约束。

#### 第二层约束:英文词组已被实体公司占据

**2FAS = Two Factor Authentication Service**,其公司主体直接叫  
**「Two Factor Authentication Service, Inc.」** —— 2015 年成立,500 万+ 下载,  
已开源(`github.com/twofas`),有浏览器扩展,支持简体中文。

→ 英文主名里放 "two factor",是正面撞这家公司的商号与品牌。

#### 第三层约束:微信生态已有大量品类名,且无一做成品牌

二次验证器 · 二步验证助手 · 两步动态验证 · 2FA 动态验证器 · MFA 二次验证码 ·  
二次验证码 Free2FA · 数字验证码 · TOTP 验证器

**它们全部用品类词命名,结果是:用户搜的是品类,记住的却不是任何一个名字。**  
这反过来构成证据 —— **品类词堆不出品牌资产**。

#### 结论:按位置分工

| 位置      | 是否带 "two factor" 语义 | 承担职责                                     |
| ------- | ------------------- | ---------------------------------------- |
| **副标题** | **必须带**             | 1 秒可懂 + 搜索命中。建议:「主名 · 双因子认证(2FA)动态口令验证器」 |
| **主名**  | **只能暗含,不能明说**       | 可注册 + 可传播。如「竹节」暗合 30 秒周期,而非直写"双因子"       |

**注意:副标题里放品类词不受第十一条影响** —— 副标题本就是描述性说明文字,  
不承担独占性,恰恰是它的正确用法。

#### 方法论修正:前几轮漏了两类更前置的检查

- **B. 它在目标市场是不是已有巨头级实体造成搜索不可逆污染?**

> **前置第 0 关:拼写纠错测试(第十轮新增,排在五关之前)。**
> 把候选丢进拼写检查器 / 搜索引擎,若它**被主动纠正成另一个真实存在的词**,

#### 先解决第 1 关的一个前置问题:拟声词为什么天然吃亏

TOKO(印尼语"商店")、TIKO(毛利语"排便",世界语"抽搐",  
Hiligaynon 语"欺诈")、KIVO(世界语"猕猴桃")三个连着死,  
不是运气问题,而是**拟声词做全球品牌的固有缺陷**:

各民族语言会**各自独立地**发明相近的音去模拟同一类现象——  
钟表声就是其中最典型的一类。所以任何从 tick / tock / 咔 / 嗒 / 哔  
派生出来的字符串,几乎必然在某个语种里撞上一个固有词。

同时它在中文侧也不讨好:拟声词属通俗口语,第 9 类注册极度密集。  
**结论:拟声词这条 vein 到此为止,不再从这里造词。**

排在被占之前 —— 就算全世界没人注册过,也不该选它。

#### 硬伤:`sectally` 会被读成 `sectionally` 的误拼

英语里有一个标准副词:

| 词              | 词性 | 含义                        | 出处                            |
| -------------- | -- | ------------------------- | ----------------------------- |
| **sectionally** | 副词 | 分节地 / 成部分地;地区性地 / 派系性地    | 剑桥、Merriam-Webster、Collins、OED 均收录 |
| — 派生自           |    | `sectional`(部分的、部门的)+ `-ly` | 词源可溯至拉丁语 `sectiō`(切割)         |

**`sectally` 去掉 `ion` 只剩 `sect` + `ally`**,而 `sect` 本身是另一个完整单词  
(宗派 / 教派,亦指"部分、切割")。拼写检查器会**主动把它判为 `sectionally`
的拼写错误** —— 这是本轮检索时实际发生的:搜 `"sectally"` 的返回结果里,  
排在最前面的就是拼写纠错页《Sectionaly or Sectionally: How To spell?》。

**后果有三条,都不是"忍一忍"能过去的**:

1. **用户拼不出来，也记不住。** 这是推广层面的致命伤 —— 比 `2fa` 那类
   展示问题严重得多。目标用户在国内更甚:拼音输入法里 `sectally` 与
   `sectionally` 完全无法区分。
2. **自动纠错会把品牌名改掉。** 邮件、输入法、浏览器、应用商店搜索框
   都会把它纠成 `sectionally`。用户找我们的时候会被系统带到别处。
3. **《商标法》第十一条风险。** 与 `doublelatch`(§6.6)同一类问题:
   近似现有通用词 → 固有显著性弱;`sect` 另有"宗派"义,  
   还可能带来**与宗教 / 派系联想**的负面歧义。

#### 域名实测(同一套 whois 脚本，`latch` 进对照组)

### 六·十、第十轮:用户点名 `seclatch` + 提出「google 式取名」—— 一次方法论修正(2026-10-04)

用户给两条:`seclatch`,以及"或者改用像 google 一样取名逻辑"。  
**第二条比第一条重要得多 —— 它指出了本项目前九轮一直在犯的方向性错误。**

#### 先说 `seclatch`:两条死因,都与 `sectally` 同类

| 检查项        | 结果                                                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **`sec` 的含义** | **是多重缩写**:second(秒/第二)、section、sector、secretary、**security**、secant(正割)、拉丁语 secundum。  
**没有一个是唯一的** —— 这正是第 1 关(显著性)最忌讳的:读者无法确定它在说什么 |
| **`latch` 的含义** | Latch Systems, Inc. 的第 9 类注册商标(**USPTO 88333287 / Reg.6909236**),商品列表写明 *software for encryption, decryption and authentication*;且 `"second latch"` 是英语既有机械术语 |
| `.com`     | **可用**(seclatch.com)                                                                                                              |

**`seclatch` = 一个歧义成分 + 一个已注册商标词根。** 两个成分各自有问题,  
拼起来不会更好。这与 §6.6 否决 `doublelatch`、§6.9 否决 `sectally` 是同一条判据。  
**域名可用不改变这个判断** —— §6.7 已经确认过"可用 ≠ 可注册",这里再加半条:  
**"`.com` 可用" 甚至不等于 "这个词有意义"。**

#### 更重要:`google` 那套逻辑到底是什么(以及它为什么能救我们)

google 的来源已有斯坦福的 David Koller 与 Google 官方双重记载(1997-09-15 注册):

```
googol  (Edward Kasner 九岁侄子 Milton Sirotta 造的数词,10^100)
   ↓  Sean Anderson 在域名注册库里打错一个字母
google  ← 无意义、可注册、好听 → Larry Page 当场决定就用它
```

**关键在于:这个"误拼"落在了一个空处。** `googol` 是生造的数词,  
改一个字母变成 `google` 之后**不撞任何现有英语词** —— 它是一个  
"看起来像英语、实际不存在"的词。这才是 google 模式真正的机制。

**对照 §6.9 的 `sectally`:`sectally` 正好死在相反方向** ——  
它的"误拼"落在了 `sectionally`(一个**真实存在的**英语标准副词)上。  
同样是差几个字母,一个落在空处(google),一个落在实词上(sectally)。

> **由此得出一条前置判据(应当排在五关之前):**
> **任何候选词,先做一次拼写纠错测试 —— 如果拼写检查器/搜索引擎会主动
> 把它纠正成另一个真实存在的词,直接淘汰,不必再查商标。**
> googol→google 不会被纠错(googol 本身也罕见);
> sectally→sectionally 会被纠错(成了"spot the typo"游戏);
> seclatch 不会被纠错,但两个成分各有问题,另一条路淘汰。

#### 按 google 模式重造的候选(whois 实测)

规则:**取一个有来源的词,做不改变读音的小改动,且改动后必须不撞现有词。**

| talletally   | 叠词                         | 可用     | 读音含糊                        |
| **talley / tallie** | tally 的变体拼写(最接近 google 手法) | **已占** | **这条正是 google 模式,但空位已被占**   |

可用率 **8/12 = 67%**。

**顺带重查 `tally` 的商标状况(补 §6.7 的粗粒度判断)**:  
`TALLY` 在 USPTO 第 9 类有多件在案,但**持有者都不在身份认证领域** ——  
Darkscreen, Inc.、Icf Next, Inc.(客户忠诚度数据分析软件)、Fellow Industries

### 六·十一、第十一轮:用户点名 `OTPAPP` —— 这不是"好不好",是"位置放错了"(2026-10-04)

用户给出 `OTPAPP`。**该词与前十轮的策略正好相反** ——  
前十轮找的是"显著性强的生造词",`OTPAPP` 是"品类名 / 描述名"。  
两条路都成立,但**不能用在同一个位置**。这一轮先把几条硬约束查清。

#### 硬约束一:微信小程序名称规则会直接驳回

微信开放文档与开发者社区的四条明文规定:

| 规定                                                                        | 出处                     |
| ------------------------------------------------------------------------- | ---------------------- |
| "不能直接使用**功能性描述、广义归纳类**的词汇作为名称 —— 此类词汇缺乏显著性且不具有识别、区分小程序的作用"             | 小程序审核:名称规则调整及优化建议      |
| "不能使用广义归纳类、普遍且不具有识别性的词汇来命名,或**在名称中包含热门搜索词及关键词堆砌,与搜索系统进行规则对抗**"           | 微信公众平台小程序运营规范 2.5      |
| "名称不是单词汇,**必须是两个词以上的组合**,当无法判断时,审核人员可主观判断"                                | 微信开放文档 1.2.1(3)        |
| "就算有**全类目的商标**,只要小程序昵称是 **4 个字以下的通用词**,也没办法通过年审"                          | 微信服务市场开发者专区官方回复        |

**官方给出的"❌ / ✔"对照,正好把 `OTPAPP` 钉在错误那一栏:**

| ❌ 不允许            | ✔ 允许（品牌词 + 品类词）         |
| ---------------- | ------------------------ |
| 壁纸、大律师、羽绒服       | 海豚壁纸、兴远大律师、海燕羽绒服         |
| **维修助手**、旅游门票预订  | **啄木鸟**维修助手、**华诚**旅游门票预订 |
| 买房、证件快照          | 团团买房、好又来证件快照             |

`OTPAPP` = **`OTP`(行业通用缩写 + 热门搜索词)+ `APP`(广义归纳类词)** ——  
两条违规同时踩中,而且"两个词组合"这条也救不了:规定要求的是  
**品牌词提供显著性**,不是把两个通用词拼起来。

**代价格外高:小程序年度只有 2 次改名机会。** 拿一个必被驳回的名称去试,  
等于白烧一次名额。

#### 硬约束二:商标注册会被引《商标法》第十一条驳回

- 第十一条第一款第(二)项:**仅直接表示商品的功能、用途等特点的标志不得注册**
- `OTP`(One-Time Password)是行业标准术语,`App` 是产品品类 ——  
  **这是能想象到的最纯粹的描述性名称,固有显著性为零**
- 第二款虽留了"经过使用取得显著特征"的口子(第二含义),  
  但那要求长期大量使用,对一个新产品不成立

#### 硬约束三:`.com` 层面,`OTP` 词根已经饱和

whois 实测 11 个 OTP 相关域名,**只有 2 个可用(18%)**:

| 状态      | 域名                                                                                                            |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| **已占(9)** | `otp` · `otpap`(用户自己持有) · **`otpapp`** · `otp-app` · `otpvault` · `otpseal` · `otplock` · `otpkey` · `onetimepassword` |
| 可用(2)    | `otptally` · `onetimelock`(都是加了后缀的)                                                                            |

18% 是**全部十一轮里密度最高的** —— 对比:两 token 复合词 29–41%、  
`tally` 一族 80%、单 token 生造词 3%。**`OTP` 词根在域名层面基本被占尽。**

而且 `otpap.com` 与 `otpapp.com` **并不相同**:用户持有的是前者(少一个 p),  
后者已属他人。「OTP App」这个读法,域名上其实并不对应。

#### 硬约束四:"OTP app"是品类检索词,不是品牌词

实测 `"OTP App"` 的搜索结果:全部是**选购指南**,不是某一家 ——  
GMX 官方帮助页标题直接就叫 *"Selection of apps for two-factor authentication  
(OTP apps)"*,榜单里是 Google Authenticator / Microsoft Authenticator / Authy /  
FreeOTP / Aegis / 2FAS / Raivo。

**我们花力气做 SEO 也抢不到这个词** —— 它属于整个品类。  
在这里投入,是给所有竞品做嫁衣。

#### 但用户的原始痛点是真的 —— 问题在于放在哪一层

回到第一轮的原话:本项目最初要改名的动因是  
**"aegis 在页面上直接显示,用户看不懂"**。`OTPAPP` 完美解决"一眼看懂",  
所以不能简单说"不行"就完了。**正确解法是分层**  
—— 这正好是 §7 已经定下的分工,只是把 `OTP` 也一并归位:

| 位置                           | 用什么                            | 为什么                   |
| ---------------------------- | ------------------------------ | --------------------- |
| **品牌名**(小程序名 / App 名 / 扩展名) | `secondtally` 之类,**必须显著**      | 要能注册、要能独占、要过微信审核      |
| **副标题 / 简介第一句**              | "OTP 验证器 · 双因子动态口令"           | 用户一眼看懂 —— 解决最初那个痛点    |
| **关键词 / 商店描述 / SEO**         | `OTP` `2FA` `TOTP` `authenticator` | 该堆的地方堆,不占品牌位          |
| **域名**                       | `otpap.com`(已有)                | **描述性域名是优点**:好记、指向明确 |

> **核心区分:域名可以是描述性的,品牌名不该是。二者不必同名。**
> `otpap.com` 是一份好资产;把 `OTPAPP` 当品牌名则是最差的选择。

#### 可执行的结论:走微信官方自己的 ✔ 模式

微信官方认可的命名模式就是 **"品牌词 + 品类词"**(✔海豚壁纸 / ✔啄木鸟维修助手)。  
所以小程序名建议直接用这个形式:

| 备选                    | 长度  | 说明                            |
| --------------------- | --- | ----------------------------- |
| **`SecondTally OTP`** | 15  | 品牌词提供显著性,品类词提供理解;在 4–30 字符内  |
| **`SecondTally 验证器`** | —   | 中文更直观,但中英混排观感略杂               |
| ~~`OTPAPP`~~          | —   | **否决**:纯通用词堆砌,过不了审也注不了册      |

#### 本轮真正的价值:它解释了前十轮为什么一直在撞墙

`OTP` / `2FA` / `多因子` / `双因子` 这类品类词根,在本赛道的  
**域名(18% 可用)、商标(描述性,不可注册)、小程序名称(明令禁止)**  
三个层面**同时饱和**。  
前九轮反复撞墙不是运气差,是**品类词根本不该进入候选池**。  
这条应当记为本项目的**结构性约束**,而不是单个词的去留。

### 六·十二、第十二轮:`tally` 用于 OTP 到底合不合适 + 「有没有更合适的词」(2026-10-04)

用户提出两个问题:① `tally` 用于 OTP 是否合适?② 是否有更合适的词?

**这是对 §6.7 头号候选的一次正当质疑 —— 我此前把 `secondtally` 推为第一顺位,  
但确实没做过适配度打分。** 补做之后,答案是"对了一半",  
而且"更合适的词"这条路的实测结果,比问题本身更有价值。

#### 问题一:tally 对 OTP 的适配度,逐项打分

符木(tally stick)的机制是:木条刻痕记录金额 → **纵向剖成两半** →  
债务人留 `foil`、债权人留 `stock` → 还债时**把两半合起来比对**才算数。  
英语里 "does it tally?"(对得上吗)就出自这里。

| 产品要传达的 | tally 能否承载 | 判断                                                                  |
| ------ | ---------- | ------------------------------------------------------------------- |
| **两个因子缺一不可** | ✅ **强**        | 「两半必须合上才算数」是双因子最贴的实物类比 —— 单持任何一半都没有意义                              |
| **免账号 / 服务器看不见** | ✅ **强**        | 符木**本身就是凭证**,不需要中央登记簿。这比"锁"类意象更准确 —— 它对应的是**去中心化的信任**,而不只是"防守" |
| **一用即核验** | ⚠️ 中       | "核对相符"是资格核验,但对**一次性**(用完即废)没有表达                                    |
| **时间 / 30 秒轮换** | ❌ **完全没有** | **这是最大缺口。** TOTP 的定义性特征就是时间窗,而符木是一块静态的木头                              |
| **保密 / 身份** | ❌ 弱        | tally 是**记账**词,与"证明你是谁"隔了一层 —— 需要解释才想得到                            |
| **中文直译** | ❌ 无        | 「符木」「木券」都不能直接用作中文名                                                  |

**结论:6 项里命中 3 项、缺 2 项。属于"对了一半"。**

#### 但真正的风险不是"缺时间",是另外两件事

**(1) `tally` 在软件语境里已经稳定等于"记账 / 表单 / 计数"**

实测 `tally` 的搜索第一页被三家占满,全部与安全无关:

| 占用者                                    | 是什么                                                         |
| -------------------------------------- | ----------------------------------------------------------- |
| **tally.so**                           | 表单 / 问卷工具,自述"powering **500,000+ teams**"、"**2 million teams**" |
| **tally.xyz**                          | 加密代币融资与治理平台,自述处理过 **\$1B** 交易量                             |
| **Tally Solutions**(tallysolutions.com) | 印度第一会计软件,36 年,**250 万企业**                                   |

USPTO 第 9 类的 `TALLY` 持有者也不是安全厂商:Icf Next(客户忠诚度数据分析软件)、  
Fellow Industries(厨房电子秤)。  
→ **用户看到 `SecondTally`,第一反应更可能是记账或表单 App,而不是验证器。**  
这属于**定位混淆**,和"语义不完整"是两回事 ——  
缺时间可以由副标题补,**定位混淆是持续损耗,补不回来**。

**(2) AI 会替我们答错**

`tally.so` 专门提供了一个 `/ai-info` 页面,开头写明  
*"This file contains structured information about Tally, intended for AI assistants  
such as ChatGPT, Claude, Perplexity, Gemini..."* —— 它的意图就是让 AI  
在被问到 "Tally 是什么" 时回答"表单和问卷平台"。

今天已经有相当比例的用户通过 AI 助手了解一个新产品。  
**未来有人问 AI「SecondTally 是什么」,AI 大概率会先关联到表单平台。**  
这是搜索污染在 AI 时代的新形态,比传统的搜索引擎污染更难逆转。

#### 问题二:"有没有更合适的词" —— 实测结果反而是个警告

按"更贴 TOTP"的思路试了两族,以及给 tally 补时间层的变体:

**族 A:沙漏 / 沙钟 —— 语义上确实比符木更贴**

沙漏同时覆盖三件事:① **时间流逝**;② **漏尽即失效**(正是 TOTP 的 30 秒窗口,  
且必须翻转重置);③ **两个玻璃球 + 中间通道**,比符木更直观的"两部分"意象。  
**但 7 个域名全部被占(7/7)** —— 连 `sandglass` `turnglass` `glasskeep`  
这类偏门拼法都没剩下。而且 Hourglass 已有多家实体:  
hourglass-app.com(耶和华见证人会众管理软件,还有中文站)、  
Hourglass Labs 的 iOS 屏幕时间控制 App(App Store id6752515297)、时间管理软件。

**族 B:票根 / 存根 —— 一次性凭证 + 恰好也是"保留的那一半"**

`counterfoil` 本身就是符木术语(债权人保留的那一半)。  
**5 个全占(5/5):** `stubkeep` `stubvault` `hourstub` `counterfoil` `foilkeep`。

**族 C:给 tally 补时间层** —— `hourtally` 占、`tallyhour` 占、`momenttally` 占,  
只有 `minutetally` 可用(但 11 个字母,读起来像 "minutely tally")。

**18 个候选只有 2 个可用(11%)—— 全部十二轮里最低的一次。**

**这不是运气问题。这是本轮最值钱的结论:**

> **"更贴切"的意象(沙漏、时钟、锁、票根、盾)是所有人第一时间都会想到的,
> 所以被占得最彻底。而符木(tally)之所以还能拿到,
> 恰恰因为它不直观。**
>
> **可得性与语义贴切度,在本赛道上是对立的。越贴切,越拥挤。**

这条与 §6.7 的结论(越贴定位的词撞车越准)是同一个机制的两面 ——  
那一条讲"为什么贴切的词被占",这一条讲"贴切的词根本轮不到你"。

#### 顺带记一个被否决的候选:`nonce`

`nonce` 是密码学里的**精确术语** —— "**n**umber used **once**",一次性随机数,  
语义上几乎是 OTP 的完美技术对应,而且短、有专业感。  
**但它在英国俚语里是极其严重的贬义(指性犯罪者),硬性否决。**

这条是"**母语者一眼看出问题、非母语者完全看不出来**"的典型。  
→ **第 1 关必须包含"俚语 / 网络用语检查",不能只查词典。**  
已补进检查清单。

#### 给用户的结论

1. **`tally` 对 OTP 是"对了一半"** —— 讲清了"两半必须合上"和"无中心账本",  
   完全没讲"时间"。
2. **但它仍是可得集合里语义最好的一档** —— 因为更贴切的都被占了(11% 可用率)。
3. **决策取决于优化哪条轴**:
   - **若看重"名字能被解释"** → `tally` 勉强够用,靠副标题补齐时间层
   - **若看重"不误导"** → `tally` 的记账 / 表单联想是真实且持续的成本,应换一个  
     **语义中性**的词 —— 这正是 Bitwarden / Mailchimp / DoorDash / Keycloak 的做法:  
     **名字不描述产品**
4. **按前十一轮已经确立的分工(品牌位放显著词、品类位放解释词),  
   第二种更一致** —— 既然品牌位本来就不需要解释产品,  
   那用一个"对了一半"的词,不如用一个**显著 + 可得 + 不误导**的中性词更稳。
5. **待用户选轴**:**"语义贴切"轴已到顶(tally 系)**;**"显著中性"轴**则回到  
   §6.7 / §6.9 / §6.10 已筛出的 `secondtally` / `twinetally` / `notchtally` /  
   `foiltally` / `halvetally` 里挑 —— 它们本来就不打算描述产品。

### 六·十三、第十三轮:用户定调「2FA 重点还是做认证」—— `symbolon` 的发现(2026-10-04)

用户一句"2fa 重点还是做认证",把语义锚点从"时间 / 凭证"**收回到"认证"本身**。  
按这条锚点重查,**找到一个真正对味的古典器物 `symbolon`** ——  
它比符木更贴本项目,因为它**专门用于身份认证,而不是记账**。

#### 发现:`symbolon` —— 古希腊的"身份凭证",且与符木是同一机制

`symbolon`(σύμβολον)是古希腊的实体凭证,**机制与符木完全一致**:  
把一件东西(陶片 / 骨片 / 戒指 / 关节骨)**劈成两半**,双方各持其一,  
**合上能严丝合缝嵌合**即证明身份或关系。

**但它的用途是认证,不是记账** —— 史料里的四种真实用法,全部是身份核验:

| 用途          | 说明                                                                    |
| ----------- | --------------------------------------------------------------------- |
| **公民大会入场凭证** | 雅典公民入 Ekklēsia 时领取陶质 symbolon,证明**合法公民身份**;散会后交回方可领津贴               |
| **陪审员身份令牌**  | 18 组青铜字母 symbolon,一面是标识符号、一面是字母,指定座席;投票后凭令领取报酬                        |
| **使者通行凭证**   | 劈成两半,一半交给信使 —— **既保安全通行,又在抵达时确认其身份**                                  |
| **抽签分配公职**   | "jigsaw" 陶片**不规则切割**,打散后重新拼合,拼上才知道哪个部族分到哪个公职 —— **防止卖官、保证政治平等** |
| **亲族相认**     | 两位亲属各出示自己的一半 symbolon,以证明亲缘关系                                          |

**这与符木的差别是决定性的:** 符木是"债的凭证",symbolon 是"**你是谁**的凭证"。  
用户说"重点做认证",`symbolon` 正是古代世界里**专为认证而造**的器物。

**还有两条附带价值:**

1. **它是 "symbol"(符号 / 象征)的词源** —— 所以有自然的现代读法,不是死词。  
   古希腊语 `symballô` = "扔到一起 / 合在一起",**"合上两半"这个动作就是"symbol"的本义**。
2. **中英天然同源(意外收获)** —— 中文的「**符**」(符节 / 兵符)是**完全一样的东西、  
   完全一样的演化路径**:都从"劈半验身份的信物"变成了"符号"。  
   §6.3 曾判定"中英同源"不可得、改走 S3 解耦;若用 symbolon 系,**中英其实天然同源,  
   不必解耦**。  
   —— **但这条只对英文侧有用**:「符」系中文已被虎符占死(§6.8,杭州虎符网络  
   自述"虎符代表身份权限……多因子身份认证")。

#### 第 0 关复核(拼写纠错测试)

`symbolon` 送进搜索引擎**未被纠正**为 `symbol`(返回的是古希腊语研究、  
东正教信经 "To Symbolon tis Pisteôs" 等正经条目,没有"你是不是想搜 symbol")。  
**第 0 关通过。** 这在 §6.9 / §6.10 之后是必须补的一步。

#### 实测:单 token 认证词根全部被占

whois 实测 18 个候选,**5 个可用(28%)**,但**8 个单 token 全部阵亡**:

| 词           | 含义           | `.com` |
| ----------- | ------------ | ------ |
| `symbolon`  | 古希腊身份凭证      | **已占** |
| `vouch`     | 担保 / 作证      | 已占     |
| `surety`    | 担保人 / 担保物    | 已占     |
| `signet`    | 图章戒指 —— 身份印鉴 | 已占     |
| `cachet`    | 封印 / 印记      | 已占     |
| `witness`   | 见证           | 已占     |
| `notary`    | 公证人          | 已占     |
| `fob`       | 钥匙坠 / 门禁牌    | 已占     |

**"认证"这条语义线上,单 token 是一个都不剩的。**  
这与 §6.12 的结论(贴切度与可得性对立)在**具体这条线上再次得到验证** ——

#### 可用的两 token 复合词(28%)

| 候选             | 构造                        | 语义                 |
| -------------- | ------------------------- | ------------------ |
| **`symbolpair`** | `symbolon` 的词根 + pair   | **一对可拼合的凭证** —— 语义最准 |
| `signetpair`   | signet(图章戒指)+ pair      | 一对印鉴               |
| `vouchpair`    | vouch(担保)+ pair          | 一对互为担保             |
| `signettally`  | signet + tally            | 印鉴 + 符木(混喻,慎)     |
| `vouchtally`   | vouch + tally             | 担保 + 符木(混喻,慎)     |

#### 诚实的结论

1. **`symbolon` 是本轮唯一"既指向认证、又含两半合上机制、还中英同源"的发现。**  
   它的语义精度高于 `tally` —— **因为 tally 是记账器物,symbolon 才是认证器物。**  
   代价:`.com` 已占(可能需要谈价)、8 个字母、非英语母语者不易拼。
2. **但 "认证" 这条线上的单 token 已全空**,能拿到的只有两 token 复合词。
3. **`symbolpair` 是这轮唯一同时满足"指向认证 + 可拼合机制 + 可得"的候选**,  
   但必须承认:**它的读感不如 `secondtally` 顺**。  
   这就是"语义贴切"这条轴的真实代价 —— 不是理论上的,是实测出来的。
4. **所以两条轴的实际差别可以量化为:**

| 轴         | 可选实例                                     | 代价                          |
| --------- | ---------------------------------------- | --------------------------- |
| **语义指向认证** | `symbolpair` / `signetpair` / `vouchpair` | 读感一般;且单 token 全空           |
| **显著 + 可得** | `secondtally` / `twinetally` / `notchtally` / `foiltally` | 不描述产品;`tally` 有记账联想         |

5. **一个折中值得单独考虑**:`symbolon` 的**中文同源词「符」系**虽然是死路(虎符),  
   但 `symbolon` 的英文侧值得作为 `tally` 的**知识资产**保留 ——  
   若日后做品牌故事,"名字来自古希腊的认证信物,也是 symbol 的词源"  
   比"来自记账用的木签"好讲得多。**这可能是选 `tally` 时最该知道的一条权衡。**

## 七、定位表述(基于全部查证结论定稿)

### 主名与副标题的分工

| 层       | 承载内容           | 理由               |
| ------- | -------------- | ---------------- |
| **主名**  | 自造词,可注册、可念、可传播 | 唯一性只能由主名提供       |
| **副标题** | 品类词 + 核心差异     | 负责被搜到,并亮出竞品打不上的牌 |

### 差异点排序(按可辩护强度,非按实现难度)

| 差异点              | 可辩护性   | 说明                                                     |
| ---------------- | ------ | ------------------------------------------------------ |
| **无需注册账号**       | **最强** | 赛道公认优势项。Ente/Proton 都要账号;2FAS 靠用户自带 iCloud 绕开;本项目天然免账号 |
| **小程序形态**        | 强      | Ente/Proton 均不覆盖,中国用户不装 App 也能用                        |
| **自部署 + 服务器无明文** | 强      | 信任模型可审计,E2E 下服务器无解密能力                                  |
| 跨端一致             | **最弱** | Ente/2FAS/Proton 全部具备,**不可作为主卖点**                      |

**结论:主打"免账号 + 小程序",而不是"支持所有平台"。**

### 推荐副标题文案

> **自造主名 · 双因子认证(2FA)动态口令验证器,小程序 / 网页 / 扩展三端一致**

把 "two factor" 的语义明确落在这里(依据见 §6.2),同时满足:  
微信"两词组合"要求、"双因子认证"搜索命中、"2FA"英文词命中、  
主语落在小程序以避开"桌面验证器"隔离性质疑。

**为什么品类词放这里是安全的**:副标题是描述性说明文字,不承担独占性,  
《商标法》第十一条约束的是"作为商标注册的标志",不影响描述性使用。

**不要写**:"支持所有平台" —— 会触发专业受众对因子隔离性的质疑,  
且被Ente Auth 的跨平台支持直接反驳。

###推广文案禁用词

- 禁用「全平台第一」「唯一支持跨端」→ 违反微信绝对化用语规则,且事实不成立
- 禁用「银行级安全」→ 金融类表述可能触发资质审核
- 禁用「免费」→ 微信明确禁止商业化用语堆砌(2.3 条)
