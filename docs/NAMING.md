## 一、定案

### 1.1 跨面命名方案

| 面                   | 用什么                                            | 依据                        |
| ------------------- | ---------------------------------------------- | ------------------------- |
| **品牌名 / GitHub 仓库** | **`secondtally`**                              | GitHub 实测 0 个同名仓库;`.com` 可用 |
| **小程序名称**           | **`SecondTally 验证器`**                          | 品牌词 + 品类词,符合微信官方 ✔ 模式     |
| **App 显示名 / 扩展名**   | `SecondTally`                                  | 无微信的"单词汇"限制,可单用品牌词        |
| **副标题 / 简介第一句**     | `OTP 验证器 · 双因子动态口令`                            | 品类词归此层                    |
| **关键词 / 商店描述**      | `OTP` `2FA` `TOTP` `authenticator`             | 该堆的地方堆,不占品牌位              |
| **域名**              | `secondtally.com`(可用)+ 已有 `otpap.com` 做文档站 / 跳转 | 开源不靠 `.com`,但主域名仍值得       |

**小程序名刻意不含 `OTP`** —— 它是热门搜索词,放进名称有触发"关键词堆砌"的风险(见 §6.3)。

### 1.2 名字的含义

**符木(tally stick)**:中世纪英格兰财政署的记账木条 —— 刻痕记下金额后
**纵向剖成两半**,债务人留 `foil`、债权人留 `stock`,还债时**把两半合起来比对**
才算数。英语里 "does it tally?"(对得上吗)即出自此。

映射到本项目:**两个因子缺一不可**(单持任何一半都无意义)+
**无中心登记簿**(符木本身就是凭证,不需要中央账本 —— 正是 E2E / 免账号的写照)。

### 1.3 取舍(已知代价,不回避)

| 优势                      | 代价                                              |
| ----------------------- | ----------------------------------------------- |
| GitHub 0 个同名仓库          | `tally` 在软件语境里有"记账 / 表单"联想(tally.so / Tally Solutions) |
| `.com` 可用               | 品牌故事已被 `yestally/tally` 讲过同一个典故                 |
| 生造词,第 0 关通过(不会被纠错)      | **完全不含"时间"层** —— TOTP 的定义性特征是 30 秒时间窗        |
| 语义命中"两半必须合上"+"无中心账本"    | `tally` 词根有 Tally Solutions(会计 ERP)等占用          |
| 两 token 复合,显著性高于单 token | —                                               |

前两条代价在**开源场景下权重下降**(开源用户来自 GitHub / HN / Reddit,不是 Google 搜 "tally");第三条由副标题补齐。

**备选**:`twinetally`(`twine` = 两股捻成一股,比 `second` 更不具描述性,
《商标法》第十一条风险更低;代价是读音略拗)。

### 1.4 小程序命名的现实路径(2026-10-04 修订)

**用户决定:暂不注册商标**(注册成功要 12–14 个月,太慢)。

#### 先纠正一个我此前的错误说法

我曾在文档里写过"商标受理通知书(TM 标)约 1 个月就能拿到,可用于小程序命名佐证"。
**这是错的。** 腾讯客服《微信认证选择商标命名方式》明文:

> **"受理中的 TM 商标,不支持商标命名。"**
> "只能使用中国商标局注册的商标 **R 商标**,不得使用境外注册的商标。"

微信开放社区亦确认:需提交**《商标注册证》(R 标)**,"**不接受《商标受理通知书》(TM 标)**"、
"不接受受理回执"。

**所以"商标"确实是一个 12–14 个月、无法提前解锁的路径 —— 用户的判断是对的。**

#### 但存在不需要商标的路径:「自选词汇」命名

同一条腾讯客服规则里还有这一句:

> "如果是通过初审的 TM 商标**只能通过自选词汇方式命名**。"
>
> **命名规则(自选词汇)**:选择自选词汇必须符合微信认证账号名称原则,即
> ① 不得侵犯注册商标专用权;② 不得与公众平台内已有账号名称重复;
> ③ 不得单独以地域名为认证名称;④ **名称不要求和公司/组织名称一致**。

**也就是说:完全不注册商标也能做小程序命名,走「自选词汇」即可。**
约束收缩为两条最实际的门槛:**不与他人重名** + **不侵犯他人商标权**。
—— 而 `secondtally` 在这两条上都是干净的(实测 GitHub 0 同名仓库;
`tally` 词根持有者均不在身份认证子领域)。

#### 另一条可用凭据:企业字号

备案实务的建议是:**没有注册商标时,尽量围绕公司名称命名,
小程序名称建议包含企业字号,并与公司经营业务保持一致。**
—— 若有公司主体,这是比商标更快的一条路。

#### 新增一道此前遗漏的关:小程序备案(工信部)

这条必须记下:**小程序名称审核 = 腾讯平台审核;小程序备案审核 = 工信部通信管理局审核。
两套独立标准,互不互通。** 管局重点核查:

> **小程序名称与企业主体、经营范围是否具备关联性。**
> 不要使用与营业执照经营范围毫无关联的泛词、通用名称。

**这条对纯生造词不利** —— `SecondTally` 本身与任何经营范围都无关联。
反过来,`SecondTally 验证器` 里的**"验证器"提供了业务关联性**,对备案有利。
**这是"品牌词 + 品类词"两段式的又一个理由**,而且比微信审核的理由更硬。

备案实务还有一条提醒:**不要先起名、等备案驳回再改** ——
改名额度宝贵,备案前就要准备 2–3 套合规备选。

#### 其余约束(一并记下)

| 项        | 内容                                                                       |
| -------- | ------------------------------------------------------------------------ |
| 名称长度     | **4–30 字符**(1 个汉字 = 2 字符)                                               |
| 改名机会     | 发布前个人 / 非个人各 **2 次**;发布后个人**每年 2 次**(自然年);企业需通过微信认证修改                   |
| 改名保护期    | 改名后原名称有 **2 天保护期**(仅限同主体)                                                |
| 特殊符号     | 仅开放 `-` `+` `&` `.`,且**包含特殊符号需提交商标材料** → `secondtally` 不含符号,不触发这一条          |

#### 待确认(阻塞路径选择)

**用户是否有公司主体(营业执照)?**

| 情况                | 后果                                                                                |
| ----------------- | --------------------------------------------------------------------------------- |
| **有企业主体**         | 可走**企业字号** + 「自选词汇」;可做微信认证拿到认证标识;类目更宽                                            |
| **仅个人主体**         | 名称保护弱(**无认证标识**,更易被他人注册相似名称);类目窄(限工具类);**且生物认证(指纹/人脸)API 不可用** —— 对 2FA 工具是功能损失 |

*注:* `wx.startSoterAuthentication`(生物认证)等高级 API 个人主体不可用;
但本项目是**免账号 + E2E** 设计,不依赖手机号与支付,所以个人主体的限制中
**只有生物认证这一条真正影响功能**。

#### 修订后的顺序(不再以商标为前置)

```
定小程序名(走「自选词汇」+ 品类词) → 微信认证命名 → 小程序备案 → 改 C 级文案
        ↑ 同时准备 2–3 套备选名,备案驳回时不必消耗改名额度
```

**商标改为可选项**:若日后要防止被抢注,再提交申请(官费 300 元/类,
申请日即产生在先权利 —— **不必等到拿到 R 标**)。

## 三、命名三层结构(不可混为一谈)

| 层          | 现状                    | 规则                                                                            |
| ---------- | --------------------- | ----------------------------------------------------------------------------- |
| **A 数据契约** | 已 `twofa.*`            | **发布后永久冻结** —— 改名 = 用户丢数据(E2E 无找回通道)                                           |
| **B 工程标识** | 已全部 `twofa`            | 包名 `@twofa/core`、Go module `twofa/server`、二进制 `twofa-server`、环境变量 `TWOFA_*`     |
| **C 展示文案** | 仍 `Aegis 2FA`,14 处      | 等主名定稿**一次到位**                                                                 |

**为什么代码层必须是 `twofa` 而不是 `2fa`** —— 语法硬约束,已实测:
`window.2fa = 1` 报 `Invalid or unexpected token`;
`export 2FA_ENV=test` 报 `not a valid identifier`。
`2fa` 只能出现在展示层文案里。

**存储键(7 处,已冻结)**:`twofa.vault.v1` / `twofa.lock.v1` /
`twofa.device.id.v1` / `twofa.device.name.v1` / `twofa.session.*` /
`twofa.web.v1.*` / `twofa.ext.v1.*`

- **前缀必须保留**:Web `localStorage` 按来源共享,裸键会与其他页面撞车,
  「清空本机数据」按前缀匹配时会误删别人的键。小程序与扩展是隔离的,Web 不是。
  (早先建议"去掉前缀"是错的,已推翻)
- 小程序侧收敛在 `platform.ts` 的 `STORAGE_NAMESPACE`,清空用 `wipeAllStorage()`,
  **不要改回列举键名**
- 护栏:`packages/core/test/storage-keys.test.mjs`(已变异验证)。
  三端各硬编码一份前缀、无共享常量也无类型约束,**漏改不会编译报错、
  也不会让任何既有测试失败** —— 原有 74 项测试全碰不到存储键

C 级 14 处清单与执行记录见 `docs/RENAMING.md`。

## 四、品牌位 vs 品类位(不要混用)

| 位置                          | 用什么                            | 为什么                    |
| --------------------------- | ------------------------------ | ---------------------- |
| **品牌名**(小程序名 / App 名 / 扩展名) | `secondtally`,**必须显著**          | 要能注册、要独占、要过微信审核        |
| **副标题 / 简介第一句**             | "OTP 验证器 · 双因子动态口令"           | 一眼看懂 —— 解决最初"用户看不懂"的痛点 |
| **关键词 / 商店描述 / SEO**        | `OTP` `2FA` `TOTP` `authenticator` | 该堆的地方堆,不占品牌位           |
| **域名**                      | `otpap.com`(已有)                | **描述性域名是优点**:好记、指向明确   |

> **核心区分:域名可以是描述性的,品牌名不该是。二者不必同名。**

"two factor" 语义与 `OTP` 都**不进主名**,全部交给副标题与关键词位。

## 五、筛查清单(顺序不可颠倒)

### 第 0 关:拼写纠错测试

把候选丢进拼写检查器 / 搜索引擎,**若被主动纠正成另一个真实存在的词,直接淘汰**,不必再查商标。

- 成立:`googol → google` 的误拼**落在空处**
- 死掉:`sectally` 会被纠成 `sectionally`(真实英语副词)
- **google 模式的真正机制是"误拼要落在空处",不是"随便拼错就行"**

### 五关

| 关卡     | 问什么                              | 不过的后果          |
| ------ | -------------------------------- | -------------- |
| 1 显著性  | 英 / 中 / 印尼-马来 / 西 / 日里是否通用词或负面义? | 注册了等于没注册(性质问题) |
| 2 搜索污染 | 第一页是否已被单一实体占据?                   | 推广费打水漂         |
| 3 商标   | 中国 9 / 42 + USPTO + EUIPO + WIPO | 排队问题,驳回即沉没成本   |
| 4 域名   | `.com` 是否可得、报价能否承受               | 决定用户对正式程度的第一印象 |
| 5 中文   | 字面是否有独立正面义?是否与既有品牌**译名**同音?      | 译名撞车最易漏        |

**第 1 关的子项 A:必须查俚语,不能只查词典。**
`nonce` 在密码学里是 "number used once" 的精确术语,语义几乎完美对应 OTP ——
**但英国俚语里是极其严重的贬义**,硬性否决。
这是"母语者一眼看出、非母语者完全看不出"的典型陷阱。

**第 1 关的子项 B:多义缩写要警惕。**
`sec` 是 second / section / sector / secretary / security / secant 的多重缩写,
**没有一个是唯一的** → 读者无法确定它在说什么。

**第 2 关要做两遍:① 传统搜索引擎第一页;② 问 AI「XX 是什么」看它怎么答。**
`tally.so` 专门提供 `/ai-info` 页面(写明 *intended for AI assistants such as
ChatGPT, Claude, Perplexity, Gemini*),意图让 AI 把 "Tally" 答成"表单平台"。
**在 AI 助手成为主要了解渠道的今天,这类污染比传统 SEO 污染更难逆转。**

**第 3 关的关键:「查不到商标」≠「没被占」—— 这是最常见的假阴性。**
只搜「关键词 + 商标 / 9 类」会命中大量 SEO 落地页。
**每个候选必须再用裸名做一次通用检索** —— 最致命的占用往往不是商标,
而是**同名的存续公司**(企业名称权在先)与**同名 App**。

## 六、九条结构性判据(比单个词的结论重要)

**1. 先问「这个词能不能被任何人独占」,再问「被谁占了」。**
前者是性质问题(排队多久都没用),后者是排队问题。

**2. 域名不是独立约束,它是"占用情况"的代理指标。**
`.com` 被占绝大多数是因为真有人在用这个名字。去掉域名门槛**救不回**被占的词 ——
只是把同一批占用挪到别的渠道去撞。
(实证:某候选看似"只因域名"被否,补查后发现西班牙 + 美国各有一家同名软件公司)

**3. 品类词根三层同时饱和 —— 整条线不可用。**
`OTP` / `2FA` / `多因子` / `双因子`:

- 域名实测仅 **18% 可用**
- 商标:《商标法》第十一条第一款第(二)项,固有显著性为零
- **微信小程序名称规则明文禁止**("不能使用功能性描述、广义归纳类词汇"
  "不能包含热门搜索词及关键词堆砌"),且官方回复称"就算有全类目的商标,
  4 个字以下的通用词也过不了年审"

**前九轮反复撞墙不是运气差,是品类词根本不该进候选池。**

**4. 安全语义词根整条线不可用。**
「守 / 盾 / 鉴 / 护 / 卫」几乎必然已被信息安全公司先占。微盾是最自然的「盾」系词,
结果 9 类 + 42 类被军工背景的芯盾集团占住,另有两家同名公司在做可信身份认证。

**5. 相邻风险取决于共用词根的持有者是否在「同一个子领域」,而不是「有没有人注册过」。**
高危:`latch`(智能门锁 + 商品列表写明 encryption/decryption/authentication)、
`sigil`(代码安全审计)、`corvid`、`bulwark`。
低危:`tally`(会计 ERP)、`cadence`(EDA)、`tempo`。
**所以 `tally` 比 `latch` 安全**,尽管前者的公司体量大得多。
另:USPTO 惯例 —— 在强商标前加弱限定词(Second)通常不足以消除混淆。

**6. 可得性与语义贴切度是对立的。越贴切,越拥挤。**
沙漏族 `.com` **7/7 全占**、票根族 **5/5 全占**、
"认证"语义单 token **8/8 全占**(symbolon / vouch / surety / signet / cachet /
witness / notary / fob)。
最直观的意象(沙漏、时钟、锁、盾、票根)是所有人第一时间都会想到的。
**符木之所以还能拿到,恰恰因为它不直观。**

**7. 语义上的"完美",恰恰是可得性上的"最差"。**
某古典词在语义上精确对应"身份认证"(还是 "symbol" 的词源),
结果**同赛道已有 IEEE 论文同名**,另有第二篇安全论文同名,
外加 30 年的同名公司、USPTO 商标、同名 App。
→ **一个词若在语义上完美对应某件事,全世界做这件事的人都会想到它 ——
包括写论文的人。别只查商标和域名,一定要查学术论文。**

**8. 越贴定位的词撞车越准 —— 已上升到隐喻层级。**
GitHub 上 `yestally/tally` 的 README 写着与我们**完全相同的符木故事**,
而且同样出自中文团队。连"为什么叫这个名字"的理由都会被同一类人独立选中。

**9. 开源场景下,GitHub 仓库名才是新的"`.com`",而且约束更紧。**
开源项目的发现渠道就是 GitHub。实测:`vouch`(mitchellh/vouch **5,119★**)、
`notary`(CNCF Notary Project **4,100★**)、`tally`(davidfowl/tally **1,164★**)、
`signet`(1,503 个同名仓库)。
**反过来,开源也松开了一个约束:本赛道领头开源项目全都不靠 `.com`**
(Aegis 官网即 `getaegis.app`;FreeOTP / andOTP / 2FAS / Raivo / KeePassXC 亦然)。
→ **"必须有好域名"这个前提在本赛道本来就不成立。**

## 八、定位表述

**主名与副标题的分工**:主名负责显著与可注册,副标题负责让人一眼看懂。

**推荐副标题**:双因子认证(2FA)动态口令验证器,小程序 / 网页 / 扩展三端一致。

**差异点排序(按可辩护强度,非按实现难度)**:

1. **免账号 + 端到端加密** —— 服务器看不到明文,无找回通道(竞品多为云同步)
2. **全平台** —— 小程序 / Web / 扩展 / App 四端(竞品 Aegis 仅 Android)
3. **自托管可选** —— 服务端开源,可自己部署
